VACUUM e ANALYZE: a faxina que mantém o banco rápido

No PostgreSQL, um UPDATE não apaga a linha antiga na hora: ele grava uma linha nova e marca a velha como morta (é o MVCC — várias versões da mesma linha, para leituras concorrentes verem dados consistentes). Pense numa planilha rabiscada: cada rasura deixa um risco. O VACUUM é a borracha que limpa esses rasgos e libera espaço; o ANALYZE atualiza as estatísticas que o planner usa no EXPLAIN. E o autovacuum é o faxineiro automático. Nesta aula: como tudo isso funciona.

Você vai aprender
  • Por que UPDATE/DELETE criam dead tuples (linhas mortas) e não liberam espaço sozinhos;
  • VACUUM, VACUUM FULL, VACUUM ANALYZE e VACUUM FREEZE — o que cada um faz;
  • ANALYZE: coleta estatísticas (pg_stats) para o planner escolher bons planos no EXPLAIN;
  • autovacuum: ligado por padrão, quando dispara e por que nunca se deve desligar;
  • O risco real do transaction ID wraparound;
  • Praticar no psql simulado: UPDATE que "não muda nada" ainda gera linha morta.

UPDATE não sobrescreve: cria versão nova

Por causa do MVCC, até um UPDATE que grava o mesmo valor cria uma nova versão da linha e marca a anterior como morta. Veja no psql — a linha some da visu, mas o espaço continua ocupado até o VACUUM:

loja_aurora=> UPDATE produtos SET estoque = estoque WHERE id = 1;
UPDATE 1
loja_aurora=> SELECT id, nome, estoque FROM produtos WHERE id = 1;
 id |   nome   | estoque
----+----------+---------
  1 | Camiseta |      20
(1 row)

O UPDATE 1 aconteceu (e no banco real deixou uma dead tuple para trás) mesmo sem mudar o valor. É por isso que rodamos muito UPDATE no banco: ele engorda o arquivo da tabela até a faxina.

VACUUM: a borracha do banco

loja_aurora=> VACUUM produtos;
VACUUM
loja_aurora=> VACUUM ANALYZE pedidos;
VACUUM
loja_aurora=> VACUUM (VERBOSE) clientes;
INFO:  vacuuming "public.clientes"
INFO:  "clientes": removed 0 rows in 0 pages
…
VACUUM

O VACUUM simples marca o espaço das linhas mortas como reutilizável (não devolve ao sistema operacional, mas novas linhas usam aquele espaço). O VACUUM FULL reescreve a tabela inteira num arquivo novo e devolve o espaço ao disco — mas trava a tabela durante o processo, então em tabela grande viva é perigoso. O VACUUM FREEZE é interno e vital: marca as linhas como "congeladas" para proteger contra o wraparound de XIDs (veja o aviso abaixo).

ANALYZE: os olhos do planner

O EXPLAIN da aula anterior mostrou rows=2550 — de onde veio esse número? Das estatísticas que o ANALYZE coleta: histogramas dos valores, os valores mais comuns, o número de linhas. Sem estatísticas boas, o planner "chuta" a rota errada e a consulta fica lenta do nada:

loja_aurora=> ANALYZE produtos;
ANALYZE
loja_aurora=> SELECT schemaname, tablename, n_live_tup, n_dead_tup, last_analyze, last_autovacuum
              FROM pg_stat_user_tables;
 schemaname | tablename | n_live_tup | n_dead_tup |        last_analyze        |     last_autovacuum
------------+-----------+------------+------------+----------------------------+--------------------------
 public     | clientes  |          5 |          0 | 2026-11-24 16:30:00.123456 | 2026-11-24 16:10:00.654321
 public     | produtos  |          5 |          1 | 2026-11-24 16:31:00.111111 | 2026-11-24 16:11:00.222222

A visão pg_stat_user_tables é o painel de saúde: n_live_tup (linhas vivas), n_dead_tup (linhas mortas esperando VACUUM), last_analyze e last_autovacuum. Se n_dead_tup só cresce, o autovacuum não está dando conta.

autovacuum: o faxineiro automático

Por padrão, o autovacuum = on: processos em segundo plano rodam VACUUM e ANALYZE sozinhos nas tabelas que mais precisam (as que acumulam mais linhas mortas proporcionalmente). Ele não bloqueia a aplicação e é a razão de você quase nunca precisar rodar VACUUM na mão.

autovacuum = on                          # nunca desligue em produção!
autovacuum_max_workers = 3
autovacuum_naptime = 1min                # de quanto em quanto tempo ele acorda
autovacuum_vacuum_threshold = 50         # mínimo de linhas mortas para agir
autovacuum_analyze_threshold = 50
Perigo grave: desligar o autovacuum parece "otimização", mas leva ao transaction ID wraparound: os IDs de transação são números de 32 bits que um dia voltam ao zero — e quando isso se aproxima, o PostgreSQL desliga o servidor de propósito para não corromper os dados. A proteção é exatamente o VACUUM FREEZE que o autovacuum roda. Além disso, sem ANALYZE o planner fica cego e os planos pioram. Conclusão: deixe o autovacuum ligado e ajuste os thresholds se uma tabela muito grande precisar de faxina mais agressiva (ex.: ALTER TABLE pedidos SET (autovacuum_vacuum_scale_factor = 0.05);).

Experimente: gere linhas mortas no simulador

Missão: rode UPDATE produtos SET estoque = estoque WHERE id = 1; — sim, gravando o mesmo valor. A saída UPDATE 1 confirma: no PostgreSQL real, essa linha virou uma dead tuple esperando o VACUUM, mesmo sem mudar nada.

Missão: apague um item: DELETE FROM itens_pedido WHERE pedido_id = 3;. O DELETE 1 marca a linha como morta — o espaço só volta com o VACUUM.

Missão: confira a "saúde" da tabela: rode SELECT COUNT(*) FROM clientes; e veja a agregação sair em (1 row) — consultas com agregação assim o planner estima usando as estatísticas do ANALYZE.

Resumo

  • MVCC: UPDATE/DELETE criam versões novas e marcam as velhas como mortas — o espaço só é reaproveitado pelo VACUUM.
  • VACUUM limpa dead tuples sem travar; VACUUM FULL devolve espaço ao disco mas trava a tabela; VACUUM FREEZE protege contra o wraparound de XIDs.
  • ANALYZE atualiza as estatísticas (pg_stats) que o planner usa para o EXPLAIN escolher Seq Scan ou Index Scan.
  • autovacuum = on faz essa faxina sozinho; nunca desligue em produção (risco de wraparound e planos ruins).
  • Monitore com pg_stat_user_tables: n_dead_tup, last_vacuum, last_autovacuum, last_analyze.
