Índices: o índice remissivo da sua planilha

Procurar um cliente pelo nome numa tabela de 5 linhas é fácil. Numa tabela de 5 milhões, sem ajuda, o PostgreSQL precisa ler linha por linha até achar — a varredura sequencial (Seq Scan). O índice resolve isso: é como o índice remissivo no fim de um livro, que leva direto à página certa em vez de folhear tudo.

Você vai aprender
  • CREATE INDEX nome ON tabela (coluna);
  • EXPLAIN: ler o plano de execução (Seq Scan vs Index Scan);
  • Quando índice ajuda (WHERE, JOIN, ORDER BY) e quando atrapalha (tabela pequena, muita escrita);
  • CREATE UNIQUE INDEX — índice + regra de unicidade.

O custo da busca sem índice

Vamos perguntar ao PostgreSQL como ele executaria uma busca pelo nome do cliente, sem executá-la de verdade: é o EXPLAIN. Na máquina ana@notebook, no banco loja_aurora:

loja_aurora=> EXPLAIN SELECT * FROM clientes WHERE nome = 'Ana Souza';
                       QUERY PLAN
---------------------------------------------------------
 Seq Scan on clientes  (cost=0.00..35.50 rows=2550 width=72)
   Filter: (nome = 'Ana Souza'::text)

Seq Scan = sequential scan, a varredura sequencial: o banco leu a tabela inteira e filtrou linha a linha (Filter). Os números de cost=0.00..35.50 são o custo estimado dessa leitura — quanto maior a tabela, maior o custo.

Criando o índice

O comando é direto: dizemos em qual tabela e em qual coluna queremos o índice remissivo:

CREATE INDEX idx_clientes_nome ON clientes (nome);
CREATE INDEX
cria um novo índice.
idx_clientes_nome
o nome do índice — convention idx_tabela_coluna, mas pode ser qualquer nome.
ON clientes
a tabela que vai ganhar o índice.
(nome)
a coluna indexada — é nela que as buscas vão ficar rápidas.
loja_aurora=> CREATE INDEX idx_clientes_nome ON clientes (nome);
CREATE INDEX
loja_aurora=> \d clientes
              Table "public.clientes"
 ...
Indexes:
    "clientes_pkey" PRIMARY KEY, btree (id)
    "clientes_email_key" UNIQUE CONSTRAINT, btree (email)
    "idx_clientes_nome" btree (nome)

Repare no \d clientes: o banco já tinha índices — todo PRIMARY KEY e todo UNIQUE criam índice automaticamente (você viu isso na aula de constraints). Agora a coluna nome também tem um.

Com o índice, o mesmo EXPLAIN no PostgreSQL de verdade mostra o caminho curto:

loja_aurora=> EXPLAIN SELECT * FROM clientes WHERE nome = 'Ana Souza';
                              QUERY PLAN
------------------------------------------------------------------------
 Index Scan using idx_clientes_nome on clientes  (cost=0.15..8.17 rows=1 width=72)
   Index Cond: (nome = 'Ana Souza'::text)

Index Scan = usou o índice remissivo: em vez de ler 2550 linhas, foi direto na página certa (cost=0.15..8.17).

No simulador: o EXPLAIN sempre responde Seq Scan — ele não guarda índices de verdade. No PostgreSQL real, com índice na coluna, aparece o Index Scan como acima.

Missão: crie o índice idx_clientes_nome na coluna nome da tabela clientes. O psql confirma com CREATE INDEX.

Missão: rode EXPLAIN SELECT * FROM clientes WHERE nome = 'Ana Souza'; e veja o plano: Seq Scan on clientes — a varredura linha a linha.

Quando usar — e quando NÃO usar

Índice não é de graça: ele ocupa espaço em disco e cada INSERT, UPDATE e DELETE precisa atualizar o índice também — ou seja, tabela com muita escrita fica mais lenta. A regra é simples: indexe o que você busca muito, não tudo.

✔ Crie índice quando…✘ Evite índice quando…
a coluna aparece muito em WHERE (nome, email)a tabela é pequena (dezenas de linhas — o Seq Scan já é barato)
a coluna é usada em JOIN (pedidos.cliente_id)a coluna tem poucos valores possíveis (baixa cardinalidade, ex.: sexo, boolean)
você ordena sempre por ela (ORDER BY data)a tabela sofre INSERT/UPDATE o tempo todo (o índice vira custo em toda escrita)
você precisa de unicidade sem ser a PK: CREATE UNIQUE INDEXvocê "acha que vai precisar" — crie índice por necessidade medida, não por achismo

Na prática: crie o índice na coluna da busca depois que a tabela crescer e a consulta começar a demorar — e meça com EXPLAIN antes e depois.

Missão: liste todos os produtos do mais caro ao mais barato: SELECT nome, preco FROM produtos ORDER BY preco DESC; (saída com (5 rows)). ORDER BY é um dos usos clássicos de índice — é a coluna que o índice remissivo ordena rapidinho.

Resumo

  • Sem índice, o PostgreSQL faz Seq Scan: lê a tabela inteira linha a linha.
  • CREATE INDEX idx ON tabela (coluna); cria o "índice remissivo" dessa coluna.
  • EXPLAIN SELECT ...; mostra o plano: Seq Scan (lento) vs Index Scan (rápido, usa o índice).
  • Índice ajuda em WHERE, JOIN e ORDER BY; atrapalha em tabela pequena ou com muita escrita.
  • PRIMARY KEY e UNIQUE já criam índice sozinhos. CREATE UNIQUE INDEX = índice + unicidade.
