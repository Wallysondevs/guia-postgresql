Projeto 1 — loja virtual Aurora

Toda loja online guarda os mesmos dados: quem compra (clientes), o que vende (produtos), os pedidos e o que vai em cada pedido (itens). Pense no banco como um arquivo de planilhas: cada tabela é uma planilha e cada linha é um registro — a diferença é que o PostgreSQL garante que as planilhas conversem entre si (um pedido só pode existir se o cliente existir). Neste projeto a Ana monta esse banco do zero, com o SQL completo.

Você vai aprender
  • A modelar 4 tabelas com PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK e DEFAULT.
  • A popular o banco com INSERT (um por linha e vários de uma vez).
  • A consultar com JOIN (cliente + pedido) e GROUP BY + COUNT/SUM (relatório de vendas).
  • Os erros reais de integridade: 23505 (email duplicado) e 23503 (pedido de cliente inexistente).

Passo 1 — o modelo: quem se relaciona com quem

Antes de escrever SQL, desenhe as relações no papel (analogia: o fichário da loja — cada ficha é uma linha de uma tabela):

RelaçãoSignificadoComo o banco garante
clientes 1 — N pedidosum cliente faz vários pedidos; cada pedido é de um só clientepedidos.cliente_id REFERENCES clientes(id)
pedidos 1 — N itens_pedidoum pedido tem vários itensitens_pedido.pedido_id REFERENCES pedidos(id)
produtos 1 — N itens_pedidoum produto aparece em vários pedidositens_pedido.produto_id REFERENCES produtos(id)
clientes.emailcada cliente tem um email únicoUNIQUE

Passo 2 — criar o banco e as tabelas (schema.sql)

O arquivo abaixo é o schema completo da loja — rode ele inteiro no psql com \i schema.sql. Note os detalhes: id integer PRIMARY KEY (o banco gera o id sozinho na prática com serial, aqui usamos id explícito para clareza), email text UNIQUE (não deixa email repetido), CHECK (preco >= 0) (não deixa preço negativo) e os REFERENCES que ligam as tabelas:

-- schema.sql — banco da loja Aurora
CREATE DATABASE loja_aurora;
\c loja_aurora

CREATE TABLE clientes (
  id         integer PRIMARY KEY,
  nome       text NOT NULL,
  email      text UNIQUE,
  cidade     text,
  estado     char(2),
  criado_em  date DEFAULT CURRENT_DATE
);

CREATE TABLE produtos (
  id       integer PRIMARY KEY,
  nome     text NOT NULL,
  preco    numeric(10,2) CHECK (preco >= 0),
  estoque  integer DEFAULT 0
);

CREATE TABLE pedidos (
  id          integer PRIMARY KEY,
  cliente_id  integer REFERENCES clientes(id),
  data        date DEFAULT CURRENT_DATE,
  status      text DEFAULT 'pendente'
);

CREATE TABLE itens_pedido (
  pedido_id   integer REFERENCES pedidos(id),
  produto_id  integer REFERENCES produtos(id),
  qtd         integer,
  preco       numeric(10,2),
  PRIMARY KEY (pedido_id, produto_id)
);

Passo 4 — as consultas que a loja usa todo dia

Clientes de um estado

loja_aurora=> SELECT nome, cidade FROM clientes WHERE estado = 'PI';
    nome    |  cidade
------------+----------
 Ana Souza  | Teresina
 Beto Lima  | Parnaíba
 Eva Nike   | Teresina
(3 rows)

Missão: liste os clientes de PI: SELECT nome, estado FROM clientes WHERE estado = 'PI'; — a saída termina com (3 rows).

Pedidos com o nome do cliente (JOIN)

O JOIN cruza duas tabelas pela chave que elas compartilham (pedidos.cliente_id = clientes.id):

SELECT c.nome, p.status
as colunas que você quer ver (apelido da tabela antes do ponto)
FROM clientes c
a tabela da esquerda, com o apelido c
JOIN pedidos p
a tabela da direita, com o apelido p
ON c.id = p.cliente_id
a condição que liga as duas: o cliente (id) é o mesmo que o pedido aponta
loja_aurora=> SELECT c.nome, p.data, p.status FROM clientes c JOIN pedidos p ON c.id = p.cliente_id ORDER BY p.data;
    nome    |    data    |  status
------------+------------+-----------
 Ana Souza  | 2026-11-20 | entregue
 Beto Lima  | 2026-11-22 | enviado
 Ana Souza  | 2026-11-23 | pendente
(3 rows)

Missão: faça o JOIN cliente + pedido: SELECT c.nome, p.status FROM clientes c JOIN pedidos p ON c.id = p.cliente_id; — a saída mostra Ana Souza com os pedidos dela.

Relatório de vendas (GROUP BY + agregações)

loja_aurora=> SELECT status, COUNT(*) AS total FROM pedidos GROUP BY status ORDER BY status;
  status  | total
----------+-------

 enviado  |     1
 pendente |     1
(3 rows)

loja_aurora=> SELECT produto_id, SUM(qtd) AS itens_vendidos FROM itens_pedido GROUP BY produto_id ORDER BY produto_id;
 produto_id | itens_vendidos
------------+----------------

          2 |              1
          3 |              3

(4 rows)

Missão: monte o relatório de itens vendidos: SELECT produto_id, SUM(qtd) FROM itens_pedido GROUP BY produto_id; — (4 rows) na saída.

Passo 5 — os erros reais de integridade

As constraints existem para impedir dado errado. Quando você tenta burlar, o PostgreSQL recusa com um código SQLSTATE (veja a cola de erros):

Erro real — 23505 (unique_violation): inserir um email que já existe: 
loja_aurora=> INSERT INTO clientes (nome, email) VALUES ('Ana Duplicada', 'ana@email.com');
ERROR:  duplicate key value violates unique constraint "clientes_email_key"
DETAIL:  Key (email)=(ana@email.com) already exists.
Solução: o email é único por cliente — use outro email ou faça UPDATE no cliente existente.

Missão: provoque o erro 23505 no simulador: INSERT INTO clientes (nome, email) VALUES ('Ana Duplicada', 'ana@email.com'); — a saída traz duplicate key value violates unique constraint.

Erro real — 23503 (foreign_key_violation): criar um pedido para um cliente que não existe: 
loja_aurora=> INSERT INTO pedidos (cliente_id) VALUES (999);
ERROR:  insert or update on table "pedidos" violates foreign key constraint "pedidos_cliente_id_fkey"
DETAIL:  Key (cliente_id)=(999) is not present in table "clientes".
Solução: insira o cliente antes (ou confira o id com SELECT id, nome FROM clientes;).

Missão: provoque o erro 23503: INSERT INTO pedidos (cliente_id) VALUES (999); — a saída traz violates foreign key constraint.

Resumo do projeto

  • Roteiro: modelar (CREATE TABLE + FK) → popular (INSERT … VALUES, confirmação INSERT 0 N) → consultar (JOIN, GROUP BY + COUNT/SUM).
  • pedidos.cliente_id REFERENCES clientes(id) é o que impede pedido órfão (erro 23503); email UNIQUE impede cliente duplicado (erro 23505).
  • Apelidos curtos (clientes c) deixam o JOIN legível: c.nome, p.status.
