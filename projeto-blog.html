Projeto 2 — blog com posts, comentários e tags

Um blog parece simples, mas esconde três relações diferentes: um post tem vários comentários (1—N), um post pode ter várias tags e uma tag aparece em vários posts (N—N) e um comentário pertence a um post e a um cliente. A analogia do arquivo ajuda: posts é uma planilha, comentários é outra — e a tabela de ligação é a ficha que diz "essa ficha vai naquela". Neste projeto a Ana monta tudo isso com SQL completo.

Você vai aprender
  • A modelar 1—N (comentarios.post_id REFERENCES posts(id)) e N—N (tabela de ligação post_tags).
  • A consultar com LEFT JOIN + GROUP BY: posts mesmo sem comentário, com COUNT.
  • A buscar texto com LIKE 'A%' e a salvar consultas em CREATE VIEW.
  • O erro 42P01: consultar uma tabela que não existe.

Passo 1 — o modelo do blog

TabelaGuardaLigação

post_tags"esse post tem essa tag"post_id → posts(id) + tag_id → tags(id), PK composta
Armadilha clássica N—N: guardar tags dentro de posts como texto ("sql, banco, tutorial") parece prático, mas aí não dá para consultar "todos os posts da tag sql" sem gambiarra. A tabela de ligação post_tags é a forma certa — cada par (post, tag) vira uma linha.

Passo 2 — criar as tabelas e popular (blog.sql)

-- blog.sql — roda dentro do banco da aplicação (ex.: \c blog)
CREATE TABLE posts (
  id           integer PRIMARY KEY,
  titulo       text NOT NULL,
  conteudo     text,
  publicado    boolean DEFAULT false,
  criado_em    timestamp DEFAULT now()
);

CREATE TABLE comentarios (
  id          integer PRIMARY KEY,
  post_id     integer REFERENCES posts(id) ON DELETE CASCADE,
  cliente_id  integer REFERENCES clientes(id),
  texto       text NOT NULL,
  criado_em   timestamp DEFAULT now()
);

CREATE TABLE tags (
  id    integer PRIMARY KEY,
  nome  text UNIQUE NOT NULL
);

CREATE TABLE post_tags (
  post_id  integer REFERENCES posts(id) ON DELETE CASCADE,
  tag_id   integer REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);

Passo 3 — as consultas do blog

Posts publicados com número de comentários (LEFT JOIN + GROUP BY)

O LEFT JOIN mantém o post mesmo quando ele não tem comentário (o INNER JOIN sumiria com ele):

loja_aurora=> SELECT p.titulo, COUNT(c.id) AS comentarios
FROM posts p LEFT JOIN comentarios c ON c.post_id = p.id
WHERE p.publicado
GROUP BY p.titulo ORDER BY p.titulo;

 Olá, PostgreSQL! |           2
(2 rows)

Busca de posts pelo título (LIKE)

loja_aurora=> SELECT titulo FROM posts WHERE titulo LIKE '%SQL%';
      titulo
------------------
 Olá, PostgreSQL!
(1 row)

Missão: treine o LIKE com curinga: SELECT nome FROM clientes WHERE nome LIKE 'A%'; — a saída traz Ana Souza (todo nome que começa com "A").

Todos os posts com suas tags (dois JOINs)

loja_aurora=> SELECT p.titulo, t.nome AS tag
FROM posts p
JOIN post_tags pt ON pt.post_id = p.id
JOIN tags t       ON t.id = pt.tag_id
ORDER BY p.titulo, t.nome;

Passo 4 — view: a consulta salva no banco

Se a consulta de "posts publicados" vive repetida no código da aplicação, salve ela como view — é uma consulta com nome, que se comporta como uma tabela de leitura:

CREATE VIEW posts_publicados AS
SELECT p.id, p.titulo, p.criado_em, COUNT(c.id) AS comentarios
FROM posts p LEFT JOIN comentarios c ON c.post_id = p.id
WHERE p.publicado
GROUP BY p.id, p.titulo, p.criado_em;
loja_aurora=> SELECT * FROM posts_publicados;
 id |      titulo      |        criado_em        | comentarios
----+------------------+-------------------------+-------------
  1 | Olá, PostgreSQL! | 2026-11-01 10:00:00     |           2
  2 | JOINs explicados | 2026-11-05 09:30:00     |           1
(2 rows)

Missão: crie uma view no simulador: CREATE VIEW v_clientes_pi AS SELECT nome, cidade FROM clientes WHERE estado = 'PI'; — o servidor responde CREATE VIEW.

Passo 5 — erro real: consultar o que não existe

Erro real — 42P01 (undefined_table): antes de rodar o blog.sql, a tabela comentarios não existe no banco novo: 
blog=> SELECT * FROM comentarios;
ERROR:  relation "comentarios" does not exist
LINE 1: SELECT * FROM comentarios;
                      ^
Solução: rode \dt para ver o que existe e \i blog.sql para criar tudo antes de consultar.

Missão: provoque o erro 42P01 no simulador: SELECT * FROM comentarios; — a saída traz relation "comentarios" does not exist.

Resumo do projeto

  • 1—N vira REFERENCES na tabela "filha" (comentarios.post_id); N—N vira tabela de ligação com PK composta (post_tags).
  • LEFT JOIN conta até quem não tem relação (COUNT viria 0); INNER JOIN some com eles.
  • LIKE 'A%' busca texto com curinga (% = qualquer texto, _ = um caractere).
  • CREATE VIEW salva a consulta no banco: depois é só SELECT * FROM nome_da_view;.
