Projeto 3 — reservas com controle de conflito

Imagine o último exemplar de um produto: dois clientes clicam "reservar" ao mesmo tempo. Sem cuidado, os dois acham que conseguiram — é o conflito de reserva (double booking). A arma do PostgreSQL contra isso é a transação: um grupo de comandos que só vale inteiro. Analogia do dia a dia: pagar no cartão — ou debita e emite o cupom, ou nada acontece. Nunca metade.

Você vai aprender
  • BEGIN abre a transação, COMMIT salva tudo, ROLLBACK desfaz tudo.
  • O prompt muda para loja_aurora* (asterisco) enquanto a transação está aberta.
  • SELECT … FOR UPDATE trava a linha e segura a segunda reserva até a primeira terminar.
  • Por que UPDATE/DELETE sem WHERE dentro de transação ainda dá para desfazer — e fora dela, não.

Passo 1 — o modelo da reserva

Além das tabelas da loja, o sistema de reservas precisa registrar quem reservou o quê:

CREATE TABLE reservas (
  id          integer PRIMARY KEY,
  produto_id  integer REFERENCES produtos(id),
  cliente_id  integer REFERENCES clientes(id),
  qtd         integer NOT NULL CHECK (qtd > 0),
  status      text DEFAULT 'ativa',   -- ativa | usada | cancelada
  criada_em   timestamp DEFAULT now(),
  UNIQUE (produto_id, cliente_id, status)  -- não deixa reservar 2x o mesmo
);

Passo 2 — reservar dentro de uma transação

A reserva mexe em duas tabelas ao mesmo tempo (diminui o estoque e cria a reserva). Se a segunda falhar, a primeira tem que voltar atrás — por isso tudo vai dentro de BEGIN … COMMIT:

loja_aurora=> BEGIN;
BEGIN
loja_aurora*> UPDATE produtos SET estoque = estoque - 1 WHERE id = 1;
UPDATE 1
loja_aurora*> INSERT INTO reservas (produto_id, cliente_id, qtd) VALUES (1, 3, 1);
INSERT 0 1
loja_aurora*> COMMIT;
COMMIT

Repare no prompt: o * no lugar do = avisa que a transação está aberta e ainda não salva. Só o COMMIT grava de verdade.

Missão 1: abra uma transação no simulador: BEGIN; — a saída mostra BEGIN e o prompt vira loja_aurora*>.

Missão 2: dentro da transação, baixe o estoque: UPDATE produtos SET estoque = 99 WHERE id = 1; — a confirmação é UPDATE 1 (só uma linha mudou).

Missão 3: crie um pedido dentro da transação: INSERT INTO pedidos (cliente_id, status) VALUES (2, 'pendente'); — INSERT 0 1 na saída.

Passo 3 — ROLLBACK: desfaz tudo

Se qualquer passo der errado (cliente não existe, estoque zerado, conexão caiu no meio), é só ROLLBACK: o banco volta exatamente para o estado de antes do BEGIN:

loja_aurora=> BEGIN;
BEGIN
loja_aurora*> UPDATE produtos SET estoque = 0 WHERE id = 1;
UPDATE 1
loja_aurora*> DELETE FROM pedidos WHERE id = 3;
DELETE 1
loja_aurora*> ROLLBACK;
ROLLBACK
loja_aurora=> SELECT estoque FROM produtos WHERE id = 1;
 estoque
---------
      20
(1 row)
loja_aurora=> SELECT COUNT(*) FROM pedidos;
 count
-------
     3
(1 row)

O estoque voltou para 20 e o pedido 3 continua lá: nada do que aconteceu dentro da transação foi gravado.

Missão 4: desfaça a transação aberta: ROLLBACK; — a saída mostra ROLLBACK e o prompt volta ao normal.

Missão 5: confirme que o ROLLBACK desfez o INSERT da missão 3: SELECT * FROM pedidos; — voltaram as (3 rows) originais.

Missão 6: rode COMMIT; sem ter aberto um BEGIN; — o servidor avisa WARNING: there is no transaction in progress e nada é gravado. (Para ver o COMMIT de verdade, abra BEGIN; antes e rode um comando qualquer dentro.)

Passo 4 — o controle de conflito: FOR UPDATE

O cenário clássico: o produto 4 (Poster) tem estoque 0… quer dizer, imagine estoque 1 e dois clientes reservando ao mesmo tempo. Sem trava, as duas sessões leem "estoque = 1" e as duas atualizam para 0 — venderam 2. Com SELECT … FOR UPDATE, a primeira sessão trava a linha e a segunda fica esperando no lock até o COMMIT:

-- sessão 1 (Ana)
loja_aurora=> BEGIN;
loja_aurora*> SELECT estoque FROM produtos WHERE id = 1 FOR UPDATE;
 estoque
---------
      20
(1 row)
loja_aurora*> UPDATE produtos SET estoque = estoque - 1 WHERE id = 1;
UPDATE 1
loja_aurora*> COMMIT;
COMMIT

-- sessão 2 (Beto): o SELECT … FOR UPDATE fica ESPERANDO até a sessão 1 dar COMMIT
-- e aí ele lê o estoque JÁ ATUALIZADO (19), não o valor antigo (20)
Erro real — lock: se uma sessão esquece o COMMIT, a linha fica travada e a outra sessão fica parada esperando (lock not available / deadlock detected). Solução: na sessão que travou, rode COMMIT; ou ROLLBACK;. Veja Problemas comuns.
Regra de bolso: toda operação que mexe em mais de uma tabela (ou que depende de uma leitura anterior) vai dentro de BEGIN … COMMIT. E toda leitura que precisa ser "a verdade do momento" para decidir algo usa FOR UPDATE.

Resumo do projeto

  • BEGIN abre, COMMIT grava, ROLLBACK desfaz — o prompt * avisa que está aberto.
  • Transação = ACID: ou tudo acontece, ou nada (atomicidade).
  • SELECT … FOR UPDATE trava a linha e serializa reservas concorrentes — Adeus, double booking.
  • Esqueceu o COMMIT? A linha fica travada para as outras sessões até você fechar a transação.
