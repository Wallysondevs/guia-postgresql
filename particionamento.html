Particionamento: dividir tabelas gigantes em fatias

Imagine a tabela pedidos com 500 milhões de linhas — um caderno de 500 mil páginas. Toda consulta varre páginas demais e o índice vira um monstro. O particionamento separa esse caderno em cadernos menores por ano: a consulta só abre o caderno do ano certo. No PostgreSQL 16 isso é declarativo: PARTITION BY RANGE (coluna). Nesta aula: criar partições, o truque do partition pruning e os cuidados.

Você vai aprender
  • Quando particionar faz sentido (dezenas/centenas de milhões de linhas, consultas por faixa) e quando não (não particione cedo demais);
  • CREATE TABLE … PARTITION BY RANGE (data) e criar partições com PARTITION OF … FOR VALUES FROM (…) TO (…);
  • Como o INSERT cai sozinho na partição certa — e o erro quando nenhuma partição cobre o valor;
  • Partition pruning: o EXPLAIN mostra que só a partição relevante é lida;
  • Os outros tipos: LIST (por estado/região) e HASH (distribuição uniforme);
  • Praticar no psql simulado: consultas por faixa de data em pedidos.

RANGE por data: um caderno por ano

O caso mais comum é particionar por faixa de datas. A tabela "pai" define a chave de partição; cada partição é uma tabela filha com um intervalo:

loja_aurora=> CREATE TABLE medicoes (
loja_aurora(>   id bigint,
loja_aurora(>   medida date NOT NULL,
loja_aurora(>   valor numeric
loja_aurora(> ) PARTITION BY RANGE (medida);
CREATE TABLE
loja_aurora=> CREATE TABLE medicoes_2025 PARTITION OF medicoes
loja_aurora(>   FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
CREATE TABLE
loja_aurora=> CREATE TABLE medicoes_2026 PARTITION OF medicoes
loja_aurora(>   FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE
PARTITION BY RANGE (medida)
Declara: esta tabela será dividida em faixas da coluna medida.
PARTITION OF medicoes
Esta é uma fatia da tabela pai — não dá para inserir nela direto, só via pai.
FOR VALUES FROM (…) TO (…)
O intervalo da fatia: FROM é inclusivo, TO é exclusivo (2026 vai até 31/12/2025 23:59…).

O INSERT na tabela pai cai sozinho na partição certa — o banco roteia a linha:

loja_aurora=> INSERT INTO medicoes VALUES (1, '2026-11-24', 36.6);
INSERT 0 1
loja_aurora=> SELECT tableoid::regclass, * FROM medicoes;
     tableoid      | id |  medida    | valor
-------------------+----+------------+-------
 medicoes_2026     |  1 | 2026-11-24 | 36.60
(1 row)

tableoid mostra em qual partição a linha foi parar. E se o valor não cair em nenhuma partição, o erro é claro:

loja_aurora=> INSERT INTO medicoes VALUES (2, '2024-05-10', 22.1);
ERROR:  no partition of relation "medicoes" found for row
DETAIL:  Partition key of the failing row contains (medida) = (2024-05-10).

Partition pruning: só abre o caderno certo

A grande vantagem aparece no EXPLAIN: com a chave de partição no WHERE, o planner descarta as partições que não interessam antes de ler qualquer dado — é o pruning (poda):

loja_aurora=> EXPLAIN SELECT * FROM medicoes WHERE medida >= '2026-06-01';
                              QUERY PLAN
-----------------------------------------------------------------------
 Seq Scan on medicoes_2026  (cost=0.00..18.10 rows=12 width=20)
   Filter: (medida >= '2026-06-01'::date)

Repare: o plano nem menciona medicoes_2025 — ela foi podada. A consulta em cima da tabela pai (medicoes) consultou só a partição 2026. Sem o WHERE na chave de partição, todas as partições são lidas (ainda assim, cada uma é menor e tem índice próprio — o que já ajuda).

Cuidados: (1) A chave de partição precisa aparecer no WHERE para haver pruning — filtre por outra coluna e todas as partições são varridas. (2) Crie a partição antes de chegar o período, ou use uma partição DEFAULT (CREATE TABLE medicoes_outros PARTITION OF medicoes DEFAULT;) para não tomar erro no INSERT. (3) Índices são criados na tabela pai e propagam para as partições: CREATE INDEX idx_medicoes_medida ON medicoes (medida); (em PG 16 dá para criar na pai e anexar os existentes). (4) Foreign keys em tabela particionada são suportadas a partir do PG 12/13 — teste na sua versão. (5) Não particione cedo demais: o overhead de gerenciar dezenas de partições não vale para tabela pequena (YAGNI).

LIST e HASH: outras formas de fatiar

TipoDivide porExemplo de usoSintaxe
RANGEFaixas ordenadas de uma coluna (datas, números)Pedidos por ano/mês; medições por períodoFOR VALUES FROM ('2026-01-01') TO ('2027-01-01')
LISTValores discretos de uma colunaPedidos por estado/região (PI, SP…)FOR VALUES IN ('PI', 'CE')
HASHHash da chave — distribui uniformementeEspalhar dados igualmente entre N partiçõesPARTITION BY HASH (id) + … 4 PARTITIONS

Também dá para compor: particionar por RANGE de data e, dentro de cada ano, por LIST de estado (subparticionamento). E dá para anexar uma tabela já existente como partição com ATTACH PARTITION — útil para trazer dados antigos de uma tabela normal.

Na prática: faixas de data em pedidos

Missão: simule a consulta "poda o caderno certo": digite SELECT * FROM pedidos WHERE data >= '2026-11-22';. Com pedidos particionado por RANGE (data), o planner leria só a partição de novembro/2026 — e a saída mostra (2 rows).

Missão: busque o pedido mais recente: SELECT * FROM pedidos ORDER BY data DESC LIMIT 1;. O LIMIT 1 com partições por data deixa a busca quase instantânea — a saída mostra a data 2026-11-23.

Missão: digite \dt para listar as tabelas do banco loja_aurora. Num banco particionado, \dt mostraria a tabela pai; cada partição aparece com \d+ e pode ser consultada direto (útil para manutenção, ex.: VACUUM só numa partição antiga).

Resumo

  • Particionar = dividir uma tabela gigante em fatias gerenciáveis: PARTITION BY RANGE/LIST/HASH.
  • RANGE por data é o caso mais comum: FOR VALUES FROM (…) TO (…) (TO é exclusivo); use partição DEFAULT como rede de segurança.
  • O INSERT na tabela pai cai na partição certa sozinho; tableoid::regclass mostra onde a linha foi parar.
  • Partition pruning: com a chave de partição no WHERE, o EXPLAIN mostra que só a partição relevante é lida.
  • Índices são criados na tabela pai e propagam para as partições; não particione tabela pequena.
