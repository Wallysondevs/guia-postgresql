Backup e restore com pg_dump e pg_restore

Imagine que o banco loja_aurora é um caderno com todas as planilhas da loja. O pg_dump tira uma fotocópia completa desse caderno num arquivo; o pg_restore (ou o psql) cola a fotocópia num caderno novo. Nesta aula: os formatos de backup, como salvar só uma tabela, e a regra de ouro — backup que nunca foi testado não existe.

Você vai aprender
  • Por que backup existe: disco queima, DELETE/TRUNCATE sem WHERE, ransomware, erro humano;
  • pg_dump em formato texto (SQL legível) e -Fc (custom, comprimido, paralelo);
  • Salvar só uma tabela com -t e um banco inteiro com todos os objetos;
  • Restaurar com pg_restore (formato custom) ou psql (formato texto);
  • A diferença entre backup lógico (pg_dump) e físico (cópia dos arquivos do disco);
  • Praticar no psql simulado: criar, gravar e esvaziar uma tabela — o drama que o backup evita.

O comando que salva o dia: pg_dump

O pg_dump roda fora do psql, no terminal da máquina (por isso o prompt é ana@notebook:~$). Ele lê o banco inteiro e gera um arquivo com os comandos SQL para recriar tudo — tabelas, dados, índices, roles:

$ pg_dump -U ana -d loja_aurora -f backup_loja.sql
$ ls -lh backup_loja.sql
-rw-rw-r-- 1 ana ana 12K Nov 24 16:20 backup_loja.sql

O -f define o arquivo de saída. Sem ele, o backup vai para a tela (útil para inspecionar). O arquivo backup_loja.sql é texto puro: dá para abrir, ler e até editar — é o "caderno fotocopiado".

pg_dump
O programa que lê o banco e gera o arquivo de backup.
-U ana
Conecta como o usuário ana.
-d loja_aurora
O banco que será fotocopiado.
-f backup_loja.sql
Grava a saída neste arquivo em vez de imprimir na tela.

Formatos: texto, custom, diretório e tar

O formato texto (padrão) é legível, mas grande e inflexível. Para produção, prefira o formato custom (-Fc): comprimido, aceita restore paralelo e permite restaurar só parte do backup:

$ pg_dump -U ana -d loja_aurora -Fc -f backup_loja.dump
$ ls -lh backup_loja.dump
-rw-rw-r-- 1 ana ana 8,4K Nov 24 16:22 backup_loja.dump
FormatoFlagComo éQuando usar
Texto SQL (plain)(padrão)Arquivo .sql legível, restaura com psqlBackups pequenos, inspección, commit em git do schema
Custom-FcBinário comprimido, restaura com pg_restoreProdução: menor, rápido e restauração seletiva/paralela
Diretório-FdVários arquivos numa pasta, restore paralelo com -jBancos grandes (vários núcleos trabalhando no restore)
Tar-FtArquivo .tarQuando outra ferramenta exige tar

Restore: colar a fotocópia num caderno novo

Restaurar é criar um banco vazio e jogar o backup dentro. Com formato custom, use o pg_restore; com formato texto, use o próprio psql:

$ psql -U ana -d postgres -c "CREATE DATABASE loja_aurora_restaurada;"
CREATE DATABASE
$ pg_restore -U ana -d loja_aurora_restaurada backup_loja.dump
$ psql -U ana -d loja_aurora_restaurada -c "SELECT COUNT(*) FROM clientes;"
 count
-------
     5
(1 row)

Para restaurar só uma tabela do backup custom: pg_restore -t pedidos -d loja_aurora_restaurada backup_loja.dump. Para salvar só uma tabela no backup: pg_dump -t pedidos ….

$ pg_dump -U ana -d loja_aurora -t pedidos -f so_pedidos.sql
$ psql -U ana -d loja_aurora -f backup_loja.sql   # restaura backup texto: replay do SQL
Perigo real: rode pg_restore num banco limpo. Num banco que já tem as tabelas, o restore dá erro de relation already exists — e a flag --clean apaga as tabelas antes de recriar. Parece util, mas se você mirar o banco errado, ela mesma destrói os dados. E a regra suprema: teste o restore numa máquina de teste todo mês. Backup que você nunca restaurou pode estar corrompido sem você saber.

Lógico vs físico: duas formas de fotocópia

Backup lógico (pg_dump)Backup físico (pg_basebackup)
O que copiaO conteúdo, em SQL/binário (recria o banco do zero)Os arquivos internos do disco, byte a byte
VantagemPortátil entre versões e máquinas; restore seletivoRestauração quase instantânea; base da replicação
DesvantagemRestore de banco grande demora (recria tudo)Só restaura a máquina/versão compatíveis; precisa de todos os arquivos
Quando usarBackup lógico periodic, migrações, "foto" do schemaRecuperação de desastre rápida, standby (ver aula de replicação)

Na prática as empresas usam os dois: pg_dump todo dia (lógico) e pg_basebackup contínuo (físico) — mas isso é assunto da aula de replicação.

O drama que o backup evita

Alguém roda TRUNCATE na tabela errada, ou um DELETE sem WHERE, às 3h da manhã. Sem backup, os dados viraram fumaça. Veja no simulador como é fácil destruir dados — e por que a fotocópia salva:

Missão: crie uma tabela de teste: CREATE TABLE teste_backup (id integer, nome text); — a saída deve mostrar CREATE TABLE.

Missão: grave um dado nela: INSERT INTO teste_backup VALUES (1, 'dado precioso'); — confirme o INSERT 0 1.

Missão: agora o acidente: rode TRUNCATE teste_backup;. A tabela esvazia na hora, sem perguntar — é exatamente por isso que o pg_dump de ontem à noite é o seu seguro.

Resumo

  • pg_dump -U ana -d loja_aurora -f backup.sql gera o backup em texto; -Fc -f backup.dump gera o formato custom comprimido.
  • Restaure texto com psql -d banco -f backup.sql; custom com pg_restore -d banco backup.dump (banco precisa existir e estar limpo).
  • -t tabela salva/restaura só uma tabela; -Fd + -j N acelera bancos grandes.
  • Lógico (pg_dump) = portável e seletivo; físico (pg_basebackup) = rápido e base da replicação.
  • Regra de ouro: teste o restore regularmente e guarde cópias em outro lugar (outro disco, outra máquina, nuvem).
