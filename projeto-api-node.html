Projeto 4 — API Node.js + pg com pool

Banco nenhum serve se a aplicação não consegue falar com ele. Neste projeto a Ana cria uma API REST que expõe a loja Aurora pela web: o navegador chama GET /clientes e a API responde com JSON tirado do PostgreSQL. A ponte entre os dois mundos é o driver pg, usando um pool de conexões — pense nele como um balcão com vários atendentes (max: 20): cada requisição pega um atendente emprestado e devolve, em vez de abrir uma porta nova no banco a cada vez.

Você vai aprender
  • A iniciar o projeto: npm init -y, npm install express pg.
  • A configurar o pool em src/db.js: new Pool({ host, database, user, password, port, max }).
  • Rotas que consultam com await pool.query('SELECT …') e respondem res.json(result.rows).
  • Tratamento de erro: conexão recusada (ECONNREFUSED) e violação de FK voltando 409.

Passo 2 — a configuração do pool (src/db.js)

Toda conexão com o PostgreSQL passa pelo Pool. As credenciais ficam em variáveis de ambiente (.env) — nunca no código:

PGHOST=localhost
PGPORT=5432
PGDATABASE=loja_aurora
PGUSER=ana
PGPASSWORD=segredo
// src/db.js — o pool de conexões com o PostgreSQL
const { Pool } = require("pg");

const pool = new Pool({
  host: process.env.PGHOST || "localhost",
  port: Number(process.env.PGPORT || 5432),
  database: process.env.PGDATABASE || "loja_aurora",
  user: process.env.PGUSER || "ana",
  password: process.env.PGPASSWORD,
  max: 20,              // até 20 conexões simultâneas no banco
  idleTimeoutMillis: 30000,  // fecha conexão ociosa depois de 30s
});

module.exports = { pool };
new Pool({…})
cria o balcão de conexões reutilizáveis com o banco
database: "loja_aurora"
o banco que a API vai usar
max: 20
limite de conexões abertas ao mesmo tempo (o resto espera na fila)
idleTimeoutMillis
descarta conexão parada para não deixar porta sobrando no servidor

Passo 3 — o servidor (src/server.js)

Três rotas: listar clientes, ver os pedidos de um cliente (com JOIN no SQL) e criar pedido (com tratamento do erro de FK):

// src/server.js — API da loja Aurora
const express = require("express");
const { pool } = require("./db");

const app = express();
app.use(express.json()); // lê o corpo JSON dos POSTs

// GET /clientes → lista todos os clientes
app.get("/clientes", async (req, res) => {
  const result = await pool.query("SELECT id, nome, email, estado FROM clientes ORDER BY id");
  res.json(result.rows);
});

// GET /clientes/:id/pedidos → pedidos do cliente, com JOIN
app.get("/clientes/:id/pedidos", async (req, res) => {
  const result = await pool.query(
    `SELECT p.id, p.data, p.status
     FROM pedidos p
     WHERE p.cliente_id = $1
     ORDER BY p.data`,
    [req.params.id]          // $1 = parâmetro seguro (sem SQL injection)
  );
  res.json(result.rows);
});

// POST /pedidos → cria pedido { "cliente_id": 1 }
app.post("/pedidos", async (req, res) => {
  try {
    const result = await pool.query(
      "INSERT INTO pedidos (cliente_id) VALUES ($1) RETURNING *",
      [req.body.cliente_id]
    );
    res.status(201).json(result.rows[0]);
  } catch (err) {
    if (err.code === "23503") {
      // foreign key: cliente não existe
      return res.status(409).json({ erro: "cliente não existe", detalhe: err.detail });
    }
    console.error(err);
    res.status(500).json({ erro: "falha interna" });
  }
});

app.listen(3000, () => console.log("API no ar em http://localhost:3000"));
// rode com: node src/server.js  (ou npm i -D nodemon e use nodemon)
Por que $1 no lugar de concatenar? "…WHERE cliente_id = " + req.params.id abre brecha para SQL injection (alguém manda 1 OR 1=1). Com $1, o driver envia o valor separado e o servidor trata como texto puro — sempre parametrize.

Erro real de conexão: se o PostgreSQL estiver fora do ar ou a senha errada, a API morre na primeira query: 
$ node src/server.js
(node:1234) UnhandledPromiseRejectionWarning: Error: connect ECONNREFUSED 127.0.0.1:5432
    at …
Error: password authentication failed for user "ana"
Solução: confira se o servidor está no ar (pg_isready), a porta (5432) e as variáveis do .env — veja Problemas comuns.

As mesmas consultas no psql simulado

Tudo que a API roda de SQL dá para testar antes no psql — é assim que se depura: copie a query da rota e rode no terminal:

Missão 1: rode no simulador a query do JOIN usada na rota: SELECT c.nome, p.status FROM clientes c JOIN pedidos p ON c.id = p.cliente_id; — a saída mostra Ana Souza.

Missão 2: simule o POST /pedidos: INSERT INTO pedidos (cliente_id, status) VALUES (3, 'pendente'); — INSERT 0 1.

Missão 3: simule o erro que a rota devolve com 409: INSERT INTO pedidos (cliente_id) VALUES (999); — a saída traz violates foreign key constraint (é esse err.code === "23503" que o catch da API captura).

Resumo do projeto

  • Roteiro: npm init -y → npm install express pg → .env com credenciais → src/db.js (pool) → src/server.js (rotas) → node src/server.js → testar com curl.
  • pool.query(sql, [params]) sempre com parâmetros $1, $2… — nunca concatene texto na query.
  • O resultado vem em result.rows (array de objetos) — é isso que vira JSON com res.json().
  • Erros do banco chegam como exceções com err.code (o SQLSTATE: 23503 = FK) — dá para traduzir em status HTTP.
