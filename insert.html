INSERT: preenchendo uma ficha nova

Tabela criada, hora de arquivar fichas: INSERT coloca uma linha nova na planilha. A ideia é a de preencher um formulário — você diz a tabela, as colunas e os valores, na mesma ordem. Vamos colocar o Zeca Silva na tabela clientes da loja_aurora.

Você vai aprender
  • INSERT INTO tabela (colunas) VALUES (valores); — com a lista de colunas;
  • Sem a lista: o VALUES preenche todas as colunas, na ordem do \d;
  • O id (PRIMARY KEY serial) se preenche sozinho;
  • Erros reais do banco: duplicate key ... unique constraint (email repetido) e foreign key constraint (pedido de cliente que não existe);
  • Conferir com SELECT depois do INSERT 0 1.

A anatomia do INSERT

INSERT INTO clientes (nome, email, cidade, estado)
VALUES ('Zeca Silva', 'zeca@email.com', 'Teresina', 'PI');
INSERT INTO
o comando de inserção
clientes
a tabela (planilha) que recebe a ficha nova
(nome, email, cidade, estado)
as colunas que você vai preencher — a lista é opcional; sem ela, o VALUES preenche TODAS as colunas na ordem da tabela
VALUES (...)
os valores, na mesma ordem das colunas; texto vai entre aspas simples
;
encerra e executa — a resposta é INSERT 0 1 (1 linha inserida)

O id aparece sozinho

Note que não passamos o id: como ele é PRIMARY KEY com serial, o PostgreSQL gera o próximo número (6, no caso). Veja a ficha arquivada:

loja_aurora=> INSERT INTO clientes (nome, email, cidade, estado) VALUES ('Zeca Silva', 'zeca@email.com', 'Teresina', 'PI');
INSERT 0 1
loja_aurora=> SELECT id, nome, email FROM clientes WHERE nome = 'Zeca Silva';
 id |   nome     |      email
----+------------+------------------
  6 | Zeca Silva | zeca@email.com
(1 row)

Também dá para inserir sem a lista de colunas — aí a ordem do VALUES tem que ser exatamente a ordem do \d clientes:

-- ordem: id, nome, email, cidade, estado, criado_em
INSERT INTO clientes
VALUES (7, 'Lia Prado', 'lia@email.com', 'Fortaleza', 'CE', '2026-11-24');

Quando o banco barra: UNIQUE e FOREIGN KEY

O INSERT não entra "a qualquer custo" — as restrições da tabela valem na hora:

loja_aurora=> INSERT INTO clientes (nome, email) VALUES ('Ana Clone', 'ana@email.com');
ERROR:  duplicate key value violates unique constraint "id_"
DETAIL:  Key (email)=(ana@email.com) already exists.

loja_aurora=> INSERT INTO pedidos (cliente_id, status) VALUES (99, 'pendente');
ERROR:  insert or update on table "pedidos" violates foreign key constraint "pedidos_cliente_id_fkey"
DETAIL:  Key (cliente_id)=(99) is not present in table "clientes".
  • UNIQUE (na coluna email): email repetido → duplicate key value violates unique constraint;
  • FOREIGN KEY (na coluna cliente_id de pedidos): não existe cliente com id = 99 → violates foreign key constraint. Um pedido precisa de um cliente de verdade.

Pratique

Missão: arquive o Zeca: INSERT INTO clientes (nome, email, cidade, estado) VALUES ('Zeca Silva', 'zeca@email.com', 'Teresina', 'PI'); → INSERT 0 1.

Missão: confira a ficha gravada: SELECT nome, email FROM clientes WHERE nome = 'Zeca Silva'; → a saída traz exatamente (1 row).

Missão: tente inserir um email que já existe: INSERT INTO clientes (nome, email) VALUES ('Ana Clone', 'ana@email.com'); → o banco barra com duplicate key.

Missão: crie um pedido para um cliente fantasma: INSERT INTO pedidos (cliente_id, status) VALUES (99, 'pendente'); → erro de foreign key.

Resumo

  • INSERT INTO t (cols) VALUES (vals); — valores na mesma ordem das colunas; texto entre aspas simples.
  • Sem lista de colunas, vale a ordem do \d t (todas as colunas).
  • Resposta INSERT 0 1 = 1 linha inserida; id serial preenche sozinho.
  • Restrições barram na hora: duplicate key ... unique constraint e foreign key constraint.
  • Sempre confira com um SELECT depois de inserir.
