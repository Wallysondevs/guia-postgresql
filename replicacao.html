Replicação: cópias vivas do banco (física e lógica)

Pense no banco loja_aurora como um caderno que vive numa máquina. A replicação física é uma fotocopiadora sincronizada: cada página nova é copiada byte a byte para outra máquina (o standby). A replicação lógica é um redator que anota cada INSERT/UPDATE/DELETE e envia só o que mudou. Nesta aula: os dois modelos, os comandos reais e os riscos.

Você vai aprender
  • Por que replicar: alta disponibilidade (failover), leitura escalada, backup sem bater no principal;
  • Replicação física: wal_level = replica, pg_basebackup, primary_conninfo, standby só-leitura e pg_ctl promote;
  • Replicação lógica: CREATE PUBLICATION / CREATE SUBSCRIPTION e quando ela é melhor;
  • Diferenças práticas entre física e lógica (tabela comparativa);
  • Riscos: réplica não é backup (DELETE replica junto) e split-brain em failover mal feito;
  • Praticar no psql simulado do banco loja_aurora.

Replicação física: o standby que copia o WAL

No PostgreSQL, toda mudança é gravada antes no WAL (write-ahead log — o "diário de rascunho" do banco). A replicação física copia esse diário, registro a registro, para a máquina secundária, que o reaplica continuamente. Resultado: uma cópia quase idêntica, atrasada em milissegundos.

No servidor primário, habilite no postgresql.conf:

wal_level = replica            # gera WAL suficiente para réplica
max_wal_senders = 10           # processos que enviam o WAL
max_replication_slots = 10     # slots de replicação
listen_addresses = '*'         # ouça na rede (firewall decide quem chega)

E crie um usuário só para replicar, com a permissão certa (na aula de permissões você viu o mínimo privilégio):

loja_aurora=> CREATE ROLE replicador WITH LOGIN REPLICATION PASSWORD 'senha-forte';
CREATE ROLE

Na máquina secundária (standby), copie a base inteira com o pg_basebackup — é o mesmo comando do backup físico da aula anterior, só que contínuo:

$ pg_basebackup -h 10.0.0.5 -p 5432 -U replicador -D /var/lib/postgresql/16/standby -Fp -Xs -R
# -Fp: formato plain · -Xs: inclui o WAL via streaming · -R: grava primary_conninfo e cria standby.signal

Com -R, o standby já nasce configurado para seguir o primário (primary_conninfo no arquivo gerado) e com o arquivo standby.signal — sem ele, a máquina subiria como servidor normal que aceita escrita.

pg_basebackup
Copia a base de dados do primário para o standby.
-h 10.0.0.5
O endereço do servidor primário.
-U replicador
Usuário com privilégio REPLICATION.
-D …/standby
Pasta de dados do servidor secundário.
-Xs -R
WAL por streaming + configura o standby automaticamente.

Failover: promover o standby a primary

Se o primário cair, o standby vira o novo principal com um toque:

$ pg_ctl -D /var/lib/postgresql/16/standby promote
# ou, em serviço systemd: sudo systemctl promote postgresql@16-standby

O promote tira o standby.signal e o servidor passa a aceitar escritas. Depois, o antigo primário precisa virar standby de novo (reconstrução com pg_rewind) — em produção, ferramentas como Patroni ou repmgr gerenciam esse failover automático.

Replicação lógica: replicar só o que interessa

A replicação lógica copia as mudanças de dados (não os bytes do disco), tabela a tabela, como uma assinatura de revista: o primário publica, o assinante recebe. Ideal para replicar só algumas tabelas, migrar entre versões ou alimentar um data warehouse:

-- no primário:
loja_aurora=> CREATE PUBLICATION pub_loja FOR TABLE clientes, pedidos;
CREATE PUBLICATION
-- no secundário (outro banco, possivelmente outra máquina):
loja_aurora_r=> CREATE SUBSCRIPTION sub_loja
  CONNECTION 'host=10.0.0.5 dbname=loja_aurora user=replicador password=senha-forte'
  PUBLICATION pub_loja;
CREATE SUBSCRIPTION

Também dá para publicar o banco inteiro: CREATE PUBLICATION tudo FOR ALL TABLES;

Replicação físicaReplicação lógica
O que copiaWAL (bytes internos) — o banco inteiro, sempreLinhas alteradas, tabela a tabela (publicações)
GranularidadeBanco inteiro; não escolhe tabelaEscolhe tabelas, colunas e até linhas (row filters)
Standby aceita escrita?Não (só-leitura até o promote)Sim — dá para escrever no assinante
Entre versões diferentesNão funcionaFunciona (ex.: 15 → 16, para upgrade sem downtime)
Uso típicoAlta disponibilidade, failover, escalar leiturasReplicar parte dos dados, CDC, integração, migrações
Riscos: (1) A réplica não é backup — um DELETE FROM clientes; no primário chega no standby em milissegundos; mantenha pg_dump além da réplica. (2) Em failover manual, tome cuidado com o split-brain: dois servidores achando que são o primary e aceitando escritas divergentes. Use uma ferramenta de orquestração (Patroni/repmgr) ou um processo claro de promote. (3) O usuário replicador precisa de senha forte e a conexão deve usar sslmode=require (aula de segurança).

Na prática, no simulador

O simulador é um único nó, mas dá para sentir a ideia: os dados que você grava aqui ficariam numa cópia idêntica no standby; e a lista de bancos mostra o que a réplica enxergaria:

Missão: digite \l e veja os bancos disponíveis — numa réplica física, o standby mostraria exatamente esta lista, cópia idêntica do primário.

Missão: grave uma linha nova: INSERT INTO clientes (nome, email) VALUES ('Replica Teste', 'replica@email.com');. No primário real, esse INSERT 0 1 entraria no WAL e chegaria no standby em instantes.

Missão: rode SELECT * FROM clientes LIMIT 3; e veja Ana Souza — no standby, a mesma consulta retornaria as mesmas linhas, uma cópia idêntica do primário.

Resumo

  • Replicação física = copiar o WAL para o standby (wal_level=replica, pg_basebackup -Xs -R); standby é só-leitura até o promote.
  • Replicação lógica = CREATE PUBLICATION / CREATE SUBSCRIPTION; replica tabelas escolhidas e aceita escrita no destino.
  • Use física para HA/failover e escalar leituras; use lógica para CDC, migrações entre versões e cópias parciais.
  • Riscos: réplica não é backup; split-brain em failover manual; proteja a conexão de replicação com SSL e senha forte.
