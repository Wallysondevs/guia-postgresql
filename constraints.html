Constraints: as regras que o banco não deixa quebrar

Uma tabela solta é como uma planilha em branco: qualquer pessoa pode escrever qualquer coisa em qualquer célula. Uma constraint é a regra impressa na capa dessa planilha que o PostgreSQL faz valer na hora — se a regra for quebrada, o comando inteiro é recusado com um erro. É assim que o banco garante que seus dados continuem fazendo sentido.

Você vai aprender
  • PRIMARY KEY — a "digital" da linha: única e obrigatória;
  • UNIQUE — o valor não pode repetir (e-mail, CPF);
  • NOT NULL — campo obrigatório, não aceita vazio;
  • CHECK — regra sobre o valor: preco >= 0;
  • FOREIGN KEY — a linha só pode apontar para outra linha que existe;
  • Os erros reais: duplicate key e foreign key constraint.

PRIMARY KEY: a digital da linha

Em uma planilha, duas linhas podem ser iguais — e aí você não sabe de qual está falando. A PRIMARY KEY (chave primária) resolve isso: é a coluna que identifica cada registro, como o CPF identifica uma pessoa. Por definição ela é UNIQUE (não repete) e NOT NULL (não pode ser vazia):

CREATE TABLE funcionarios (
  id      integer PRIMARY KEY,            -- a digital da linha
  nome    text    NOT NULL,               -- obrigatório
  email   text    UNIQUE,                 -- não pode repetir
  salario numeric CHECK (salario > 0)   -- só valor positivo
);
id
o nome da coluna que vai identificar a linha.
integer
o tipo da coluna (número inteiro).
PRIMARY KEY
a regra: essa coluna é única e obrigatória — a identidade da linha.

UNIQUE: ninguém repete o valor

O e-mail do cliente precisa ser único — não dá para ter dois cadastros com o mesmo e-mail. A constraint UNIQUE cria essa regra e um índice por baixo dela (já já veremos índices). Se alguém tentar cadastrar de novo:

loja_aurora=> INSERT INTO clientes (nome, email) VALUES ('Ana Duplicada', 'ana@email.com');
ERROR:  duplicate key value violates unique constraint "clientes_email_key"
DETAIL:  Key (email)=(ana@email.com) already exists.
Erro real: duplicate key

O comando inteiro é recusado — nenhuma linha entra na tabela. Repare na mensagem: duplicate key value violates unique constraint diz qual regra foi quebrada, e o DETAIL mostra o valor que já existe. É o banco protegendo sua planilha de cadastros repetidos.

Missão: tente cadastrar outro cliente com o e-mail ana@email.com, que já existe. O psql responde ERROR: duplicate key value violates unique constraint ... e nada é inserido.

FOREIGN KEY: só aponta para quem existe

A tabela pedidos guarda cliente_id — o número da ficha do cliente que fez o pedido. Essa coluna tem uma FOREIGN KEY (chave estrangeira): REFERENCES clientes(id). Traduzindo para o dia a dia: "esse número precisa existir na tabela clientes". Não pode existir pedido de cliente fantasma:

CREATE TABLE pedidos (
  id         integer PRIMARY KEY,
  cliente_id integer REFERENCES clientes(id),   -- foreign key
  data       date DEFAULT CURRENT_DATE,
  status     text DEFAULT 'pendente'
);
loja_aurora=> INSERT INTO pedidos (cliente_id) VALUES (999);
ERROR:  insert or update on table "pedidos" violates foreign key constraint "pedidos_cliente_id_fkey"
DETAIL:  Key (cliente_id)=(999) is not present in table "clientes".
Erro real: foreign key constraint

O cliente 999 não existe, então o pedido é recusado: violates foreign key constraint. Essa integridade referencial é o que impede o banco de virar um arquivo bagunçado, cheio de pedidos apontando para nada. Dá para completar a regra com ON DELETE CASCADE (apaga os pedidos junto com o cliente) ou ON DELETE RESTRICT (proíbe apagar o cliente enquanto houver pedidos).

Missão: insira um pedido para o cliente 999, que não existe. O psql bloqueia na hora: ERROR: ... violates foreign key constraint "pedidos_cliente_id_fkey".

CHECK e NOT NULL: regras sobre os valores

NOT NULL diz que a coluna não pode ficar vazia — o nome do cliente é obrigatório. CHECK (expressão) aceita qualquer regra sobre o valor: na tabela produtos, preco >= 0, ou seja, não existe produto com preço negativo:

loja_aurora=> INSERT INTO produtos (nome, preco) VALUES ('Camiseta promo', -5);
ERROR:  new row for relation "produtos" violates check constraint "produtos_preco_check"
loja_aurora=> INSERT INTO clientes (nome, email) VALUES (NULL, 'semnome@email.com');
ERROR:  null value in column "nome" of relation "clientes" violates not-null constraint

O CHECK aceita qualquer comparação: estado IN ('PI', 'SP', 'PE'), qtd > 0, email LIKE '%@%' — o que a sua regra de negócio exigir.

Resumo

  • Constraint = regra que o PostgreSQL faz valer: se quebrada, o comando inteiro é recusado com erro.
  • PRIMARY KEY = UNIQUE + NOT NULL — a digital da linha.
  • UNIQUE: valor não repete → erro duplicate key.
  • NOT NULL: campo obrigatório. CHECK (expr): regra sobre o valor.
  • FOREIGN KEY ... REFERENCES: só aponta para linha que existe → erro foreign key constraint.
