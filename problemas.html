Problemas comuns de PostgreSQL — e como resolver

Todo mundo trava no PostgreSQL em alguma hora — a boa notícia é que cada erro já diz o código SQLSTATE e a causa. Nesta página estão as trombadas que mais aparecem no dia a dia (conexão, senha, banco/tabela inexistente, lock, permissão), cada uma com a mensagem real, a causa e o conserto. Várias dá para provocar de propósito no psql simulado abaixo.

Você vai aprender
  • O roteiro de diagnóstico: leia a mensagem inteira (ela traz ERROR/FATAL, o SQLSTATE e às vezes HINT).
  • Conexão recusada (08006), senha errada (28P01), banco não existe (3D000) — os três da hora de conectar.
  • Tabela não existe (42P01), chave duplicada (23505), chave estrangeira (23503), lock (55P03/40P01).
  • Permissão negada e o perigo do UPDATE/DELETE sem WHERE.

O roteiro de diagnóstico (sempre nesta ordem)

  1. Leia a mensagem inteira — ERROR vs FATAL (FATAL = a conexão cai na hora).
  2. Anote o SQLSTATE (5 caracteres) e procure na cola de erros.
  3. Se tiver LINE 1: … ^, a setinha marca a coluna exata do problema no seu comando.
  4. Se tiver HINT:, o próprio servidor está sugerindo a solução — leia ele.

1. "Connection refused" — não conecta no servidor

Erro real (08006): 
$ psql -h localhost -U ana loja_aurora
psql: error: connection to server at "localhost" (127.0.0.1), port 5432 failed: Connection refused
        Is the server running on that host and accepting TCP/IP connections?

Causa: o servidor PostgreSQL está parado, ou está em outra porta/host. Solução: teste com pg_isready; suba o serviço (sudo systemctl start postgresql no Linux, ou abra o app/Docker); confira a porta padrão 5432 com psql -p 5432 ….

2. "password authentication failed" — senha errada

Erro real (28P01): 
$ psql -U ana loja_aurora
Password for user ana:
psql: error: connection to server at "localhost" (::1), port 5432 failed: FATAL:  password authentication failed for user "ana"

Causa: senha incorreta (ou o pg_hba.conf exige método diferente, ex.: scram-sha-256 vs md5). Solução: confira a senha; para trocar: sudo -u postgres psql e ALTER USER ana PASSWORD 'nova_senha';; no psql, \password ana.

3. "database does not exist" — banco errado

Erro real (3D000): 
$ psql -U ana loja_aurora_typo
psql: error: connection to server at "localhost", port 5432 failed: FATAL:  database "loja_aurora_typo" does not exist

Causa: nome do banco com erro de digitação. Solução: liste os bancos com psql -U ana -l (ou \l dentro do psql) e conecte no nome certo; se precisar criar: CREATE DATABASE loja_aurora;.

Missão: provoque o 3D000 no simulador: \c banco_fantasma → FATAL: database "banco_fantasma" does not exist.

4. "relation does not exist" — tabela não existe

Erro real (42P01): 
loja_aurora=> SELECT * FROM clientes;
ERROR:  relation "clientes" does not exist
LINE 1: SELECT * FROM clientes;
                      ^
Possíveis causas: digitou errado, esqueceu de rodar o CREATE TABLE, está no banco errado, ou usou maiúscula sem aspas (Clientes ≠ "Clientes").

Solução: \dt lista as tabelas do banco atual; SELECT current_database(); diz em qual banco você está; rode o script do schema (\i schema.sql).

Missão: provoque o 42P01: SELECT * FROM tabela_fantasma; → relation "tabela_fantasma" does not exist.

5. "duplicate key value violates unique constraint" — valor repetido

Erro real (23505): 
loja_aurora=> INSERT INTO clientes (nome, email) VALUES ('Outra Ana', 'ana@email.com');
ERROR:  duplicate key value violates unique constraint "clientes_email_key"
DETAIL:  Key (email)=(ana@email.com) already exists.

Causa: a coluna tem UNIQUE (ou é PK) e o valor já existe. Solução: use outro valor, faça UPDATE na linha existente, ou use upsert: INSERT … ON CONFLICT (email) DO UPDATE SET nome = EXCLUDED.nome;.

Missão: provoque o 23505: repita o email ana@email.com → duplicate key value….

6. "violates foreign key constraint" — referência quebrada

Erro real (23503): 
loja_aurora=> INSERT INTO pedidos (cliente_id) VALUES (999);
ERROR:  insert or update on table "pedidos" violates foreign key constraint "pedidos_cliente_id_fkey"
DETAIL:  Key (cliente_id)=(999) is not present in table "clientes".

Causa: o cliente_id não existe em clientes — ou você está apagando um cliente que tem pedidos. Solução: insira o pai antes; confira com SELECT id FROM clientes;; para apagar em cascata, declare a FK com ON DELETE CASCADE.

Missão: provoque o 23503: INSERT INTO pedidos (cliente_id) VALUES (999); → violates foreign key constraint.

7. Lock / deadlock — transação esquecida segurando a linha

Erros reais (55P03 / 40P01): 
loja_aurora=> BEGIN;
loja_aurora*> UPDATE produtos SET estoque = 5 WHERE id = 1;
UPDATE 1
-- (esqueceu o COMMIT… em outra sessão:)
loja_aurora=> UPDATE produtos SET estoque = 6 WHERE id = 1;
-- fica ESPERANDO no lock…
ERROR:  deadlock detected

Causa: uma sessão fez BEGIN + UPDATE e não fechou a transação — a linha fica travada para as outras. Solução: na sessão travada, rode COMMIT; ou ROLLBACK;; para investigar, consulte pg_locks e pg_stat_activity.

8. "permission denied for table" — usuário sem acesso

Erro real (42501): 
loja_aurora=> SELECT * FROM clientes;
ERROR:  permission denied for table clientes

Causa: o usuário conectado não tem GRANT na tabela (todo objeto tem dono). Solução: como superuser: GRANT SELECT, INSERT ON clientes TO ana; — veja a aula usuários e permissões; confira quem você é com SELECT current_user;.

9. "syntax error at or near" — comando mal formado

Erro real (42601): 
loja_aurora=> SELEC * FROM clientes;
ERROR:  syntax error at or near "selec"
LINE 1: SELEC * FROM clientes;
        ^

Causa: palavra-chave errada, vírgula sobrando, ou ordem errada (SELECT … FROM … WHERE … GROUP BY … ORDER BY … LIMIT). Solução: a setinha ^ mostra exatamente onde o servidor parou.

Missão: provoque o 42601: SELEC * FROM clientes; → syntax error at or near "selec".

10. Meta-comando inválido no psql

Erro real do psql: 
loja_aurora=> \xablau
Invalid command \xablau. Try \? for help.

Causa: meta-comando que não existe. Solução: \? lista todos os meta-comandos válidos.

Missão: digite um meta-comando inventado: \xablau → Invalid command \xablau. Try \? for help.

11. O clássico: UPDATE/DELETE sem WHERE apagou a tabela

Perigo real: 
loja_aurora=> DELETE FROM produtos;
DELETE 5   -- apagou TUDO. Sem WHERE, o comando vale para todas as linhas.

Solução: o hábito salva: BEGIN; → rode o comando → confira com SELECT → se estiver certo, COMMIT;, se não, ROLLBACK;. Dentro da transação dá para voltar atrás; fora dela, já era.

Checklist quando travar

$ pg_isready                      « 1. o servidor está no ar? (porta 5432)
$ psql -U ana -l                  « 2. quais bancos existem?
loja_aurora=> \dt                  « 3. quais tabelas existem neste banco?
loja_aurora=> \d clientes          « 4. quais colunas e constraints?
loja_aurora=> SELECT current_database(), current_user;   « 5. onde estou e quem sou?
