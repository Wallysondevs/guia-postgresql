EXPLAIN: como o PostgreSQL executa sua consulta

Antes de dirigir, o GPS traça a rota. O EXPLAIN faz isso com a sua consulta: mostra o plano de execução que o PostgreSQL escolheu — se vai ler a tabela inteira (Seq Scan, como folhear a planilha linha a linha) ou pular direto pelo índice (Index Scan, como ir à página certa pelo sumário). Nesta aula: ler esse plano e achar consultas lentas.

Você vai aprender
  • EXPLAIN SELECT … mostra o plano sem executar a consulta;
  • Ler Seq Scan vs Index Scan/Bitmap Index Scan e os números cost, rows, width;
  • EXPLAIN ANALYZE executa de verdade e mede o tempo real (e BUFFERS mostra os blocos lidos);
  • Por que o planner pode errar a rota sem estatísticas boas (aula de ANALYZE);
  • Praticar no psql simulado até a saída mostrar Seq Scan on.

Seu primeiro plano de execução

Coloque EXPLAIN na frente de qualquer SELECT e o PostgreSQL responde com o plano, sem rodar a consulta:

loja_aurora=> EXPLAIN SELECT * FROM clientes;
                        QUERY PLAN
-----------------------------------------------------------
 Seq Scan on clientes  (cost=0.00..35.50 rows=2550 width=72)

Tradução: Seq Scan on clientes = "vou varrer a tabela clientes inteira, linha por linha". cost=0.00..35.50 é o custo estimado (o primeiro número é o custo para entregar a primeira linha; o segundo, para entregar todas). rows=2550 é a estimativa de linhas que vão sair; width=72 é o tamanho médio de cada linha em bytes. No simulador os números são fixos; num banco real eles mudam conforme o tamanho real da tabela — é exatamente o que o ANALYZE atualiza.

Missão: digite EXPLAIN SELECT * FROM clientes; no terminal e ache o Seq Scan on clientes no plano — o PostgreSQL vai ler a tabela inteira, sem índice.

Seq Scan vs Index Scan: planilha inteira vs sumário

Sem índice na coluna do WHERE, o banco não tem escolha: varre tudo (Seq Scan). Com índice, ele consulta o sumário e pula direto (Index Scan):

loja_aurora=> CREATE INDEX idx_clientes_estado ON clientes (estado);
CREATE INDEX
loja_aurora=> EXPLAIN SELECT * FROM clientes WHERE estado = 'PI';
                                    QUERY PLAN
-----------------------------------------------------------------------------------
 Bitmap Heap Scan on clientes  (cost=4.30..12.50 rows=3 width=72)
   Recheck Cond: (estado = 'PI'::bpchar)
   ->  Bitmap Index Scan on idx_clientes_estado  (cost=0.00..4.29 rows=3 width=0)
         Index Cond: (estado = 'PI'::bpchar)

Com poucos registros o planner ainda pode preferir o Seq Scan (ler tudo é mais barato que abrir o índice) — e isso é certo: o custo é relativo ao tamanho da tabela. O índice brilha quando a tabela é gigante e o WHERE filtra poucas linhas (isso é o seletividade).

Tipo de nóO que significaQuando aparece
Seq ScanSem índice útil, ou tabela pequena, ou o filtro pega quase tudo
Index ScanUsa o índice para achar as linhas diretoWHERE em coluna indexada e muito seletiva
Bitmap Index Scan + Bitmap Heap ScanÍndice gera um "mapa de bits" das páginas e lê só elasFiltros em várias colunas indexadas
Nested Loop / Hash Join / Merge JoinComo o banco junta duas tabelas (JOIN)Consultas com JOIN
Sort / Aggregate / LimitOrdenação, GROUP BY, LIMIT do planoConsultas com ORDER BY, agregações, LIMIT

EXPLAIN ANALYZE: medir o tempo real (com cuidado!)

O EXPLAIN puro só estima. Com ANALYZE, o PostgreSQL executa a consulta de verdade e mostra o tempo real por nó — por isso é a ferramenta favorita para achar gargalos:

loja_aurora=> EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM pedidos WHERE cliente_id = 1;
                                                      QUERY PLAN
-----------------------------------------------------------------------------------------------------------------------
 Seq Scan on pedidos  (cost=0.00..35.50 rows=2550 width=72) (actual time=0.012..0.045 rows=3 loops=1)
   Filter: (cliente_id = 1)
   Rows Removed by Filter: 2547
   Buffers: shared hit=4
 Planning Time: 0.080 ms
 Execution Time: 0.061 ms
EXPLAIN
Pede o plano de execução em vez do resultado.
(ANALYZE, BUFFERS)
ANALYZE = executa e mede o real; BUFFERS = mostra blocos de disco/memória lidos.
actual time=… rows=…
Tempo real e linhas reais por nó — compare com a estimativa rows=2550.
Rows Removed by Filter
Linhas lidas e descartadas — se for muito alto, falta índice.
Cuidado: EXPLAIN ANALYZE executa o comando. Num SELECT tudo bem; num UPDATE/DELETE/INSERT os dados mudam de verdade! Se quiser só medir sem risco, envolva numa transação e desfaça: BEGIN; EXPLAIN ANALYZE UPDATE …; ROLLBACK;

Experimente: ache o Seq Scan no simulador

Missão: digite EXPLAIN SELECT * FROM pedidos WHERE cliente_id = 1;. Sem índice em cliente_id, o plano mostra Seq Scan on pedidos — a tabela de pedidos seria varrida inteira para achar os pedidos de um só cliente.

Missão: agora com análise real: digite EXPLAIN (ANALYZE) SELECT COUNT(*) FROM produtos; e veja o plano com Seq Scan on produtos e a linha de tempo real (actual time).

Resumo

  • EXPLAIN SELECT … mostra o plano sem executar; EXPLAIN (ANALYZE, BUFFERS) … executa e mede o real (cuidado com UPDATE/DELETE).
  • Seq Scan = tabela inteira; Index Scan/Bitmap Index Scan = usa índice; o planner escolhe pelo cost estimado.
  • Compare rows (estimado) com actual … rows (real): quando divergem muito, rode ANALYZE na tabela.
  • Rows Removed by Filter alto demais = sintoma clássico de falta de índice na coluna do WHERE.
