Segurança: SSL, pg_hba.conf e boas práticas

Se o banco loja_aurora é um prédio, o arquivo pg_hba.conf é a portaria: cada linha diz quem pode entrar, vindo de onde, e como prova quem é (senha, certificado). E o SSL é o túnel blindado na calçada — sem ele, a senha viaja legível pela rede. Nesta aula: ler o pg_hba.conf, exigir criptografia e fechar as portas.

Você vai aprender
  • Como o pg_hba.conf decide cada conexão (tipo, banco, usuário, IP, método) e a ordem das linhas;
  • Métodos de autenticação: trust, peer, scram-sha-256, cert — e quando cada um faz sentido;
  • Ativar SSL no servidor (ssl = on) e exigir na conexão (sslmode=require);
  • Erros reais de acesso negado: FATAL: no pg_hba.conf entry… e password authentication failed;
  • Boas práticas: menor privilégio (aula anterior), senhas fortes, porta 5432 longe da internet, atualizações;
  • Praticar no psql simulado: tentar conectar num banco que não existe e listar os bancos visíveis.

pg_hba.conf: a portaria do banco

O arquivo pg_hba.conf (hba = host-based authentication) fica em /etc/postgresql/16/main/ e é lido de cima para baixo: a primeira linha que casar com a conexão vale. Cada linha tem 5 campos:

# TIPO   BANCO        USUÁRIO      ENDEREÇO          MÉTODO
local    all          postgres     peer
local    all          all          peer
host     all          all          127.0.0.1/32      scram-sha-256
host     all          all          ::1/128           scram-sha-256
hostssl  loja_aurora  app          0.0.0.0/0         scram-sha-256
host     loja_aurora  all          10.0.0.0/8        reject
hostssl
Só vale se a conexão usar SSL (criptografada) — o túnel blindado é obrigatório.
loja_aurora
O banco que essa regra cobre (ou all).
app
O usuário permitido nessa regra.
0.0.0.0/0
Qualquer IP da internet (máscara de rede) — restrinja ao IP do servidor da aplicação!
scram-sha-256
Método de autenticação: senha com hash moderno (nunca md5 hoje em dia).

Depois de editar o arquivo, aplique sem derrubar as conexões: SELECT pg_reload_conf(); no psql (ou $ sudo systemctl reload postgresql no terminal).

Métodos de autenticação: da portaria aberta ao certificado

MétodoComo funcionaQuando usar
trustEntra sem senha nenhumaNunca em rede; só em teste local
peerConfere se o usuário do sistema operacional é o mesmo do bancoConexões locais no próprio servidor (local)
password / md5Senha pela rede (md5 hoje é considerado fraco)Evite; prefira scram
scram-sha-256Senha com troca criptografada moderna (padrão atual)O padrão para produção
certAutentica com certificado do cliente (mTLS)Máquinas confiáveis, automação, zero senhas na rede
Perigo clássica: uma linha host all all 0.0.0.0/0 trust significa "qualquer pessoa de qualquer lugar entra como qualquer usuário sem senha". É a porta do prédio escancarada. Se a conexão não casar com nenhuma linha, o erro é direto: FATAL: no pg_hba.conf entry for host "…", user "…", database "…". E se a senha estiver errada: FATAL: password authentication failed for user "ana".

SSL: criptografar a conexão até o servidor

Sem SSL, tudo que você digita no psql — inclusive a senha — trafega legível pela rede (alguém com um sniffer na mesma rede lê tudo). No servidor, ligue o SSL em postgresql.conf e aponte os certificados:

ssl = on
ssl_cert_file = '/etc/ssl/certs/ssl-cert-snakeoil.pem'
ssl_key_file  = '/etc/ssl/private/ssl-cert-snakeoil.key'
# para produção, gere certificados reais (Let's Encrypt / CA interna),
# com permissão 0600 no arquivo da chave

Do lado do cliente, o psql escolhe o modo com sslmode. Na máquina da Ana, conectando no banco por SSL:

$ psql "host=notebook dbname=loja_aurora user=ana sslmode=require"
Senha para o usuário ana: ************
psql (16.4)
SSL connection (protocol: TLSv1.3, cipher: TLS_AES_256_GCM_SHA384)
loja_aurora=> \conninfo
You are connected to database "loja_aurora" as user "ana" on host "notebook" (address "10.0.0.5") at port "5432" via SSL.

Boas práticas que fecham o prédio

  • Menor privilégio: a aplicação entra com um usuário só dela, com GRANT mínimo (veja usuários e permissões); o superuser postgres só entra localmente, via peer.
  • Senhas fortes e trocadas: no psql, ALTER USER app WITH PASSWORD '…'; considere pgcrypto para guardar senhas dos seus usuários com hash.
  • Não exponha a 5432 na internet: deixe o banco atrás de firewall/VPN; o pg_hba.conf deve listar só os IPs dos servidores de aplicação.
  • Atualize o PostgreSQL: versões velhas têm vulnerabilidades públicas — aplique os minor releases.
  • Logue acessos: log_connections = on e log_disconnections = on em postgresql.conf para saber quem entrou e quando.
  • Separe ambientes: banco de teste nunca aponta para o de produção.

Missão: no simulador, tente entrar num banco que não existe para você: digite \c banco_secreto. A "portaria" barra na hora com FATAL: database "banco_secreto" does not exist — em um servidor real, um banco sem GRANT CONNECT daria permission denied.

Missão: digite \l para listar os bancos aos quais você tem acesso. Só loja_aurora (e postgres) aparecem — usuário comum não vê o prédio inteiro, só o que a portaria deixa.

Resumo

  • pg_hba.conf decide cada conexão: tipo (local/host/hostssl), banco, usuário, IP e método — a primeira linha que casa vale.
  • Use scram-sha-256 para senhas em rede, peer no local, cert para máquinas; trust só em teste.
  • SSL no servidor: ssl = on + certificados; no cliente: sslmode=require (ou verify-full em produção).
  • Erros de barreira: no pg_hba.conf entry… e password authentication failed.
  • Nunca exponha a 5432 na internet; mantenha o PostgreSQL atualizado e logue as conexões.
