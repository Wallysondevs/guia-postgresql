Usuários e permissões: quem pode fazer o quê no banco

Pense no banco de dados como um prédio comercial: a tabela clientes é uma sala com documentos. Nem todo mundo pode entrar em todas as salas — o CREATE USER cria a pessoa (com login e senha), e o GRANT entrega a chave da sala certa, só com as permissões necessárias. Nesta aula: criar roles, dar e tirar acessos, e o lema do menor privilégio.

Você vai aprender
  • A diferença entre USER e ROLE (no PostgreSQL, usuário é uma role com LOGIN);
  • CREATE USER/CREATE ROLE com senha, e listar todo mundo com \du;
  • GRANT SELECT/INSERT… ON tabela TO usuario e REVOKE para tirar;
  • Roles de grupo (ex.: equipe_leitura) para não dar permissão um a um;
  • O erro permission denied for table e por que a aplicação nunca deve usar superuser;
  • Praticar no psql simulado (ana@notebook, banco loja_aurora, PostgreSQL 16).

USER é uma ROLE com LOGIN

Desde a versão 8.1, o PostgreSQL unificou os conceitos: todo usuário é uma role, mas só a role com o atributo LOGIN pode entrar com senha. Pense assim: ROLE é o cargo ("vendedor", "gerente"); USER é a pessoa física que exerce o cargo e passa na portaria.

loja_aurora=> CREATE ROLE vendedor LOGIN PASSWORD 'senha-forte-123';
CREATE ROLE
loja_aurora=> CREATE USER maria WITH PASSWORD 'outra-senha-456';
CREATE ROLE
loja_aurora=> \du
   Role name   |                         Attributes
---------------+------------------------------------------------------------
 ana           | Create DB
 maria         | 
 postgres      | Superuser, Create role, Create DB
 vendedor      |

Repare no \du: ele lista as roles e seus atributos. postgres é o superuser — a chave mestra do prédio. A sua aplicação nunca deve usar essa chave.

Missão: no terminal abaixo, digite \du e aperte Enter. Você deve ver a lista de roles com o atributo superuser — é assim que se descobre quem manda no banco.

GRANT: entregar a chave da sala certa

O GRANT concede privilégios sobre um objeto (tabela, schema, banco) para uma role. A sintaxe é direta: conceda isto, neste objeto, para esta role.

loja_aurora=> GRANT SELECT ON clientes TO vendedor;
GRANT
loja_aurora=> GRANT SELECT, INSERT, UPDATE ON pedidos TO vendedor;
GRANT
loja_aurora=> GRANT ALL PRIVILEGES ON produtos TO maria;
GRANT
GRANT
A ordem: concede privilégios.
SELECT, INSERT
Os privilégios na tabela (ler, inserir, alterar, apagar…).
ON pedidos
O objeto: a "sala" que a chave abre.
TO vendedor
A role que recebe a chave.

REVOKE: pegar a chave de volta

O REVOKE faz o contrário — e vale a regra de ouro: quem pode dar, pode tirar. Se o vendedor acessa pedidos e depois isso muda, é um REVOKE:

loja_aurora=> REVOKE INSERT, UPDATE ON pedidos FROM vendedor;
REVOKE
loja_aurora=> REVOKE ALL PRIVILEGES ON produtos FROM maria;
REVOKE

Quando um usuário sem permissão tenta ler a tabela, o PostgreSQL barra na hora:

loja_aurora=> SELECT * FROM clientes;
ERROR:  permission denied for table clientes
Cuidado: dar GRANT ALL para a role da aplicação é como dar a chave mestra para o porteiro — se a aplicação for invadida (SQL injection), o invasor apaga tudo. Siga o princípio do menor privilégio: conceda SELECT numa tabela só se a aplicação realmente só lê nela, e INSERT/UPDATE/DELETE só onde precisa escrever.

Privilégios comuns em tabelas

PrivilégioO que permiteExemplo típico
SELECTLer linhas (SELECT)Role de leitura/relatórios
INSERTInserir linhas novasApp que cadastra pedidos
UPDATEAlterar linhas existentesApp que muda status do pedido
DELETEApagar linhasQuase nunca para aplicação — restrito a admins
TRUNCATEEsvaziar a tabela inteira de uma vezLimpeza de tabela temporária
ALL PRIVILEGESTodos os anteriores de uma vezSó para o dono da tabela / manutenção

Também existem privilégios em outros objetos: USAGE e CREATE em schemas (para usar/criar tabelas dentro da "pasta"), e CREATE no banco (para criar schemas). Para dar acesso ao banco inteiro de uma vez: GRANT CONNECT ON DATABASE loja_aurora TO vendedor;

Roles de grupo: permissões em equipe

Em vez de dar GRANT para cada pessoa, crie uma role de grupo sem login e entregue a ela as permissões; depois encaixe as pessoas nesse grupo — como colocar funcionários numa equipe:

loja_aurora=> CREATE ROLE equipe_leitura;
CREATE ROLE
loja_aurora=> GRANT SELECT ON clientes, produtos, pedidos TO equipe_leitura;
GRANT
loja_aurora=> GRANT equipe_leitura TO maria, vendedor;
GRANT ROLE

Agora maria e vendedor herdaram o SELECT das três tabelas. Para tirar alguém da equipe, basta REVOKE equipe_leitura FROM maria; — um comando só, sem caçar permissões uma a uma.

Missão: no simulador você está conectado como ana, que tem permissão de leitura em clientes. Digite SELECT nome, email FROM clientes LIMIT 2; e confirme que a consulta retorna Ana Souza.

Missão: tente gravar um cliente repetido: INSERT INTO clientes (nome, email) VALUES ('Ana Souza', 'ana@email.com');. O banco barra com duplicate key — a restrição UNIQUE do email protege os dados independente de quem está logado, desde que tenha INSERT.

Resumo

  • Usuário = role com LOGIN: CREATE USER maria WITH PASSWORD '…' (ou CREATE ROLE … LOGIN).
  • GRANT SELECT, INSERT ON tabela TO role; concede; REVOKE … FROM role; tira.
  • Roles de grupo (sem login) organizam permissões em equipe: GRANT equipe TO pessoa;
  • Sem permissão, o erro é ERROR: permission denied for table ….
  • Princípio do menor privilégio: a aplicação nunca usa postgres (superuser); cada role pega só a chave das salas de que precisa.
  • Veja as roles existentes com \du no psql.
